### 二、 架构详细描述
该架构采用了**分层解耦**的设计思想，将前端交互、后端网关、智能体逻辑、模型服务与数据存储分离，确保系统具备高可维护性与扩展性。

#### 1. 前端展现层
*   **技术栈**: Next.js + React
*   **职责**:
    *   提供聊天交互界面，支持 Markdown 渲染（用于展示 SQL 和 Python 代码高亮）。
    *   处理用户的模型切换操作（本地/外部模型选择），并将配置参数随请求发送。
    *   接收后端的流式响应，实现打字机效果，提升用户体验。

#### 2. 后端服务层
*   **技术栈**: Python + Quart Framework
*   **职责**:
    *   **API 网关**: 作为统一入口，处理鉴权、参数校验和请求分发。
    *   **异步处理**: 利用 Quart 的异步特性，支持大模型推理过程中的长连接与流式传输，避免阻塞线程。
    *   **缓存加速**: 集成 **Memcached**，对热门问题或中间结果进行缓存，减少对大模型和数据库的重复调用。

#### 3. 智能体逻辑层
这是系统的核心大脑，基于 **LangGraph + LangChain + SemanticRouter** 构建。

*   **Semantic Router (语义路由)**:
    *   作为请求的第一站。利用向量相似度匹配，快速判断用户意图是“查询数据”还是“生成代码”。
    *   避免了传统硬编码 `if-else` 的脆弱性，能够理解“查一下有多少人”和“写个脚本查人数”的区别。
*   **LangGraph (状态图编排)**:
    *   **SQL Agent**: 专门处理“查数”意图。包含“Schema 检索 -> SQL 生成 -> SQL 执行 -> 结果总结”的闭环流程。如果 SQL 执行报错，它会触发“自我修正”循环，重新生成 SQL。
    *   **Code Agent**: 专门处理“写代码”意图。根据用户需求生成可执行的 Python 脚本。
    *   **Memory**: 管理对话上下文，支持多轮对话追问，确保 Agent 知道上文提到的“这个表”是指哪个表。

#### 4. 大模型服务层
*   **技术栈**: LangChain Model Abstraction
*   **职责**:
    *   **模型切换器**: 这是一个抽象接口层。根据前端传来的参数，动态实例化不同的模型对象。
    *   **本地模型**: 通过 Ollama 或 vLLM 部署的本地大模型（如 Qwen, Llama 3），保证数据隐私安全，无网络延迟。
    *   **外部模型**: 对接 OpenAI 或 DeepSeek 等在线 API，利用其更强大的推理能力处理复杂任务。

#### 5. 数据存储层
*   **技术栈**: PostgreSQL + PgVector
*   **职责**:
    *   **PostgreSQL**: 存储业务数据（用户实际要查的数据）以及对话日志。
    *   **PgVector**: 存储数据库元数据的向量索引。
        *   **核心价值**: 当用户提问时，系统不需要把整个数据库的所有表结构都塞给大模型（会导致 Token 溢出），而是通过向量检索，只找出与问题最相关的几张表的结构定义，极大地提高了 SQL 生成的准确率。

### 三、 核心交互流程描述
1.  **用户发起请求**: 用户在 Next.js 前端输入“查询 users 表记录数”，并选择“本地模型”。
2.  **网关接入**: Quart 接收请求，首先查询 Memcached 是否有相似问题的缓存，若无则进入智能体层。
3.  **意图识别**: Semantic Router 分析语义，判定为“数据查询意图”，将请求转发给 **SQL Agent**。
4.  **知识增强 (RAG)**: SQL Agent 提取关键词“users”，去 PgVector 中检索 `users` 表的字段定义和注释。
5.  **模型推理**: Agent 构造 Prompt（问题+表结构），通过模型切换器调用本地大模型，生成 `SELECT count(*) FROM users;`。
6.  **执行与反馈**: Agent 在 PostgreSQL 中执行该 SQL，获取结果（如 `100`）。若执行成功，再次调用大模型将数字转化为自然语言：“users 表中目前有 100 条记录”。
7.  **响应返回**: 结果经由 Quart 流式返回给前端展示。
